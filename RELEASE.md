## Ensure builds are green:

* [GitHub Actions](https://github.com/rabbitmq/rabbitmq-dotnet-client/actions)


## Update API documentation

Note: `main` (`6.x` and later) only

Please see [this guide](https://github.com/rabbitmq/rabbitmq-dotnet-client/blob/main/APIDOCS.md).


## Update CHANGELOG

Run `tools/generate-changelog.sh` with the previous tag and the new tag:

```
tools/generate-changelog.sh v7.X.Y v7.X.(Y+1)
```

This inserts a new section into `CHANGELOG.md` after the `# Changelog` header.
The release date is set to `UNRELEASED-DATE` as a placeholder. Review the
output with `git diff CHANGELOG.md` and edit as needed before committing.


## Create and push release tag

Note: `alpha` releases are versioned by default via the MinVer package. The version is based off of the most recent tag.

RC release:

```
git tag -a -s -u B1B82CC0CF84BA70147EBD05D99DE30E43EAE440 -m 'rabbitmq-dotnet-client v7.X.Y-rc.1' 'v7.X.Y-rc.1'
```

Final release:

```
git tag -a -s -u B1B82CC0CF84BA70147EBD05D99DE30E43EAE440 -m 'rabbitmq-dotnet-client v7.X.Y' 'v7.X.Y'
```

Push!

```
git push --tags
```

## `6.x` branch


### Trigger build locally

```
cd path\to\rabbitmq-dotnet-client
git checkout v6.X.Y
git clean -xffd
.\build.bat
dotnet build ./RabbitMQDotNetClient.sln --configuration Release --property:CONCOURSE_CI_BUILD=true
dotnet nuget push -k NUGET_API_KEY -s https://api.nuget.org/v3/index.json ./packages/RabbitMQ.Client.6.X.Y.nupkg
```

## `main` (`7.x`) branch

### Release-note prose

`CHANGELOG.md` is generated by `tools/generate-changelog.sh` and carries only the mechanical PR and issue list. `HISTORY.md` duplicates the older half of it and nothing regenerates it. User-visible behavior notes (dashboards moving, error rates changing, deprecations) live in `docs/release-notes/X.Y.Z.md`.

A pull request that changes user-visible behavior adds its note to that file in the same commit as the change, and carries the `release-notes` label. Writing the note beside the code is what gets it reviewed, versioned and diffable, and what keeps a claim about the previous release measured against the released version rather than against an earlier state of the branch.

Nothing enforces the pairing. The label marks which pull requests should have touched the file, so before cutting a release, check each one against it:

```
gh pr list --repo rabbitmq/rabbitmq-dotnet-client \
    --state merged --search 'milestone:X.Y.Z label:release-notes' \
    --json number,title,url
```

### Cut the release

* Reconcile `docs/release-notes/X.Y.Z.md` against the label query above, and commit any note that is missing
* Close the appropriate milestone, and make a note of the link to the milestone with closed issues visible
* Create the release as a draft with the notes file as its body: `gh release create vX.Y.Z --draft --notes-file docs/release-notes/X.Y.Z.md`, append the generated changelog links with `gh release edit`, then publish. Publishing triggers the NuGet push, so the body has to be finished first
* GitHub actions will build and publish the release to NuGet

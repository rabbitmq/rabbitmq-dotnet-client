# 7.3.0

User-visible behavior changes. `CHANGELOG.md` carries the full merged pull request and issue list.

## Security

- **Field tables and arrays nested more than 32 levels deep are now rejected** (GHSA-qhmm-xgrg-q669). Reading one recursed without a limit, so a `connection.start` from the broker, or message headers set by any publisher, could overflow the stack and terminate the application. Such a value now fails the connection and every channel on it, as an unknown field type already did: `CreateConnectionAsync` throws `BrokerUnreachableException`, and a delivery, a `basic.return` or a `BasicGetAsync` reply closes the connection with reply code 502. Deeper nesting was read before, and this client still publishes it, so a mandatory message it cannot route closes the publisher's own connection when it is returned. A message carrying such headers closes the connection again each time it is redelivered. From RabbitMQ 4.0, a quorum queue's default delivery limit eventually removes it; on other queues it stays until removed, for example by purging the queue, or on a stream until retention discards it.
- **`BasicGetAsync` no longer waits forever when the reply's headers cannot be read.** It throws the parse error, such as `SyntaxErrorException`, and the connection closes with reply code 502.

## Publishing a caller-owned or sequence body

Adds API and breaks implementors of `IChannel` (#1913, #1983):

- **`IChannel` gained four new abstract members, with no default implementations.** The interface went from two `BasicPublishAsync` overloads to six, the new ones taking an `IDisposable? bodyOwner` alongside either a `ReadOnlyMemory<byte>` or a `ReadOnlySequence<byte>` body. Any type implementing `IChannel` directly, such as a test double or a decorator, will not compile against 7.3.0 until it implements them. This is the release's only hard source break, and it affects implementors rather than callers. Five new `[Obsolete]` warnings also fail a warnings-as-errors build; they are listed below.
- A body can now be published from a `ReadOnlySequence<byte>` without being copied. Ten new `IChannelExtensions` overloads take `bodyOwner`, five of them for a sequence and five for a `ReadOnlyMemory<byte>`. Ownership of `bodyOwner` transfers to the client, which disposes it once, after the message reaches the wire or when publication fails, so every segment must stay valid and unmodified until then. Passing `null` is permitted but copies the body into one pooled buffer.

## OpenTelemetry span status and duration

Two changes visible to anyone with dashboards or alerts on this client's spans (#1978):

- **Publish span duration rises by about an order of magnitude** when publisher confirmations and confirmation tracking are both enabled, because the span now covers the confirmation round trip. The span also now starts before flow control, so a broker under a memory or disk alarm moves it even with confirmations off. Nothing became slower. Latency dashboards keyed on the `publish` span will move; `docs/internal/opentelemetry-tracing-review.md` has the measurements.
- **Failed operations now produce `Error` spans.** Publisher and subscriber spans previously set no status, so a throwing consumer traced as a success, as did a nacked or returned publish on a channel with confirmations and tracking both enabled. They now set `Error`, `error.type` and an exception event, so error rates keyed on these spans go from zero to real. Cancellation the caller's own token requested is exempt and rethrows unmarked; a client-internal timeout, such as `RequestedConnectionTimeout`, is recorded as an error with `error.type` of `BrokerUnreachableException`.

## OpenTelemetry tracing configuration

Now owned per connection (#2026, #2009):

- A connection's tracing configuration can be set on the factory, via `ConnectionFactory.TracingOptions`, instead of only through process-wide statics. Every member of the new `ConnectionTracingOptions` is nullable and `null` means inherit, resolved per member, so setting one span-shaping flag leaves whatever propagation is configured process-wide untouched.
- Propagation is configured with a `DistributedContextPropagator`, not a pair of delegates. `RabbitMQActivitySource.ContextInjector`, `ContextExtractor`, `UseRoutingKeyAsOperationName` and `TracingOptions` are now `[Obsolete]` warnings, so a warnings-as-errors build touching any of them fails; they keep working and will be removed in a future major version. `ContextInjector` and `ContextExtractor` are replaced by `ConnectionTracingOptions.Propagator`, `UseRoutingKeyAsOperationName` by the member of the same name on `ConnectionTracingOptions`, and `TracingOptions` by `ConnectionFactory.TracingOptions`.
- Assigning `null` to `RabbitMQActivitySource.ContextInjector`, `ContextExtractor` or `TracingOptions` now throws `ArgumentNullException` at the assignment, instead of surfacing as a `NullReferenceException` from inside the client on a later publish or delivery.
- Per-`TracerProvider` configuration remains unachievable, and the `RabbitMQ.Client.OpenTelemetry` README now says so, along with the three activity sources, their span names, and both options. One `ActivitySource` produces a single `Activity` shared by every listener, and one publish injects a single set of headers, so neither span shape nor propagated context can differ per provider. Where the configuration needs an owner, configure the factory.
- `RabbitMQ.Client.OpenTelemetry` adds `ConnectionFactory.UseOpenTelemetryTracing`, which installs propagation on a factory and is the entry point to use in a generic-host application, where the factory is resolved after `WithTracing` runs. Subscribing a provider with `AddRabbitMQInstrumentation` still installs the process-wide propagation default as a side effect; separating the two is #2042.
- Installing `RabbitMQ.Client.OpenTelemetry` lifts the application to `System.Diagnostics.DiagnosticSource` 10.x, whose default propagator emits baggage in the standard `baggage` header rather than the non-standard `Correlation-Context` that 9.x uses, and encodes the value differently. This reaches the wire only for connections still using the client's own default propagation: `UseOpenTelemetryTracing`, `AddRabbitMQInstrumentation` and `ConnectionTracingOptions.Propagator` all route through OpenTelemetry's own propagator instead. #2040 carries it.

## OpenTelemetry semantic-convention conformance

Span names, span kinds and attribute names change to follow the RabbitMQ semantic convention (#1980):

- **`messaging.rabbitmq.delivery_tag` is renamed to `messaging.rabbitmq.message.delivery_tag`, with no transition period.** The old name is gone in 7.3.0. It carried the value correctly, so any dashboard, alert or saved query keyed on it returns **no results** after upgrading, silently, rather than erroring. Search your observability configuration for the old name before you upgrade. A dual-emit period was considered and rejected: it would trade one silent break now for the same break in 8.0.0, plus a duplicate tag on every fetch and delivery span until then.
- Messaging span names and span kinds change. Span names now include the exchange; `messaging.destination.name` is composed rather than the bare exchange; `BasicGet` spans are `Client` rather than `Consumer`; and an empty `BasicGet` reports `fetch` with `messaging.rabbitmq.message.received` set to `false`. Set `UseRoutingKeyAsOperationName` to `false` for bare operation names.
- **`messaging.message.body.size` and `messaging.message.envelope.size` are no longer emitted by default.** Both are Opt-In in the convention, which asks instrumentation to populate them only when configured to. Set `IncludeMessageSizes` on `RabbitMQTracingOptions`, or per connection on `ConnectionTracingOptions`, to get them back.
- `messaging.destination.name`, `messaging.operation.name` and `messaging.operation.type` are now supplied at span creation, so samplers can key on them, and they survive on spans sampled as `PropagationData`. `network.transport` is newly emitted.
- Three attributes this client emits are its own rather than the convention's: `messaging.rabbitmq.message.received`, `messaging.rabbitmq.connection.is_reconnection` and `messaging.rabbitmq.connection.automatic_recovery`. The registry defines only `messaging.rabbitmq.destination.routing_key` and `messaging.rabbitmq.message.delivery_tag` under that prefix. Treat the other three as this client's, not as specified telemetry: they may be renamed or withdrawn.
- Every `messaging.*` attribute in the convention is Development rather than Stable, so these names may move again.

## Connection close and abort timeouts

The caller's value is now honored, and an abort is always bounded (#1973):

- A graceful close timeout is honored as given, down to a one second minimum. Any value below 30 seconds was silently raised to 30 seconds, so a `CloseAsync(TimeSpan.FromSeconds(6))` that could not complete burned 30 seconds before giving up. A close that completes normally was never affected. A small minimum remains, because the timeout also bounds the close handshake itself: below it, the close cancels itself before transmitting `connection.close` and the connection is left open on the broker even though the client reports it closed. `CloseAsync(TimeSpan.Zero)`, and any negative value other than `Timeout.InfiniteTimeSpan`, therefore resolve to one second.
- `Timeout.InfiniteTimeSpan` is honored as a graceful close timeout. It is documented as the way to wait without a bound, but being negative it compared below the floor and was lowered to 30 seconds. Know what it costs: against a peer that has stopped reading, such a wait ends only when the broker notices our silence and drops the connection, roughly two to three minutes at the default heartbeat interval and **never at all if heartbeats are disabled**. A close the broker answers completes as soon as it replies.
- **An abort is now capped at 10 seconds**, where it previously honored any value the timer could express and threw `ArgumentOutOfRangeException` above that. The 5-second minimum is retained, so the effective band is 5 to 10 seconds. `AbortAsync(Timeout.InfiniteTimeSpan)` now waits up to 10 seconds rather than 5. On a connection with automatic recovery enabled, which is the default, both close and abort first stop the recovery loop on a separate `RequestedConnectionTimeout` budget, so the total can exceed the value you passed.
- A graceful close timeout above roughly 24.86 days, including `TimeSpan.MaxValue`, is clamped rather than throwing `ArgumentOutOfRangeException` before the connection begins shutting down. The ceiling is the same on every target framework, so a `net8.0` caller asking for 30 days now gets 24.86 rather than the 30 the timer would have accepted. Only `Timeout.InfiniteTimeSpan` gives up the bound entirely.
- A close or abort that reaches its timeout now closes the socket. The forced close was a no-op in that case, because it was handed the token whose expiry had just produced the failure, so the socket and its file descriptor were left for the garbage collector to reclaim rather than closed. See #2022.

## Timeouts above about 24.86 days

`RequestedConnectionTimeout`, `ContinuationTimeout`, `HandshakeContinuationTimeout`, `SocketReadTimeout` and `SocketWriteTimeout` above roughly 24.86 days, including `TimeSpan.MaxValue`, are now clamped to that (#2029). Such a value could throw `ArgumentOutOfRangeException` from inside the client, so connecting reported a reachable broker as `BrokerUnreachableException`, or every channel RPC threw. On `net8.0`, a `RequestedConnectionTimeout` or `ContinuationTimeout` between 24.86 and about 49.7 days used to be honored and is now shortened to 24.86 days. The properties still return the value assigned.

## Channel and rate limiter disposal

Four behaviors change (#1988):

- **A caller-supplied publisher-confirmation rate limiter is no longer disposed with the channel.** If you pass your own `RateLimiter` to the `CreateChannelOptions` constructor, its lifetime is now yours: code that relied on channel disposal to dispose it must dispose it itself. The old behavior was the defect, because that limiter is shared by every channel created from the same options and reused across every automatic recovery, so a channel disposing it broke the survivors. This stops the channel disposing any limiter, including the one the library supplies.
- **`ThrottlingRateLimiter` now releases its inner limiter when it is disposed asynchronously.** `await limiter.DisposeAsync()` previously disposed nothing, so the inner limiter leaked and the limiter went on handing out leases. Code that disposes a limiter asynchronously and then keeps using it will now see `ObjectDisposedException`.
- Disposing a channel on a connection with automatic recovery enabled now disposes the underlying channel, and each recovery disposes the channel it replaced. Previously both were abandoned, so every recovery cycle left another dispatcher and its work queue unreclaimed.
- A channel being disposed concurrently with an inbound delivery no longer risks tearing down the whole connection. Such a delivery raised `ChannelClosedException` on a path with no handler, and the connection's receive loop reported it as an internal error, so the entire connection shut down instead of the one channel closing. The delivery is now dropped.

## Dropped deliveries keep their pooled body

Previously the body was left to the garbage collector (#2039):

- When the consumer dispatcher drops a delivery, that delivery's body now goes back to `ArrayPool<byte>.Shared`. It drops one for every delivery still in flight when a channel begins closing, so this was ordinary operation rather than an edge case; `docs/internal/consumer-dispatch-concurrency.md` carries the measured split for one configuration. Applications that open and close channels while consuming should see less allocation afterwards. No API changes, and nothing a consumer callback observes changes.

## Consumer dispatch concurrency of zero

No longer silently broken (#2035):

- **A `ConsumerDispatchConcurrency` of `0` is now treated as `1`.** Passing zero, on `ConnectionFactory` or through the `CreateChannelOptions` constructor, previously built a channel with no reader loops at all: consumers registered successfully and then never received anything, while queued deliveries held their pooled buffers for the lifetime of the channel. Nothing reported it. `ushort` remains the only ceiling, because a large value does what it says whereas zero never did anything useful. One wrinkle remains: because the `CreateChannelOptions` constructor defaults its parameter to `1` rather than `null`, a factory-level setting is not inherited by explicitly constructed options unless you pass `consumerDispatchConcurrency: null`. See #2027 and #2054.

## Closing a connection during recovery

No longer reported as an internal error (#1997, #2037):

- Closing a connection while recovery is invoking one of your topology-recovery callbacks is no longer reported that way. Recovery released an internal semaphore around each callback and re-acquired it with the recovery token, so once a close had begun the re-acquire threw and the resulting `SemaphoreFullException` replaced the real cancellation. This affected the `RecoveringConsumerAsync`, `QueueNameChangedAfterRecoveryAsync` and `ConsumerTagChangeAfterRecoveryAsync` events and every `TopologyRecoveryExceptionHandler` callback; one recorded consumer on the recovering channel plus a close was enough, with no subscriber of yours needed.
- Recovering a consumer now carries the recovery cancellation token. `basic.consume` was re-issued with no token, so closing a connection during recovery could park on the channel's RPC semaphore for an unbounded multiple of `ContinuationTimeout` before the request was even sent. Cancelling a token does not shorten the wait for a reply already in flight; `docs/internal/connection-shutdown-and-cancellation.md` has the detail.
- Closing a connection after automatic recovery has reconnected, but before it finishes, now reports reply code 200 `ClosedDuringRecovery` rather than 541 `FailedAutoRecovery` (#2037). Recovery still aborts the connection it opened, so the reply code and timeout passed to `CloseAsync` do not apply. A close while recovery is still reconnecting reports the reason the connection was lost.

## Connection-level tracing

New in this release (#1734):

- A third activity source, `RabbitMQ.Client.Connection`, now emits `connection attempt` and `tcp connection attempt` spans. There were two sources before. `connection attempt` carries `messaging.rabbitmq.connection.is_reconnection`, and on the attempts `ConnectionFactory` makes also `.automatic_recovery`, which records whether the factory has automatic recovery enabled. Note the span-volume consequence: a broker outage with automatic recovery enabled emits one `connection attempt` span per retry plus one `tcp connection attempt` span per endpoint tried, rather than nothing.

## Channel state across automatic recovery

Previously discarded whenever the connection recovered (#2031):

- A channel's `ContinuationTimeout` and `DefaultConsumer` now survive automatic recovery. The timeout reverted to whatever the channel's `CreateChannelOptions` held, which for an options object shared across connections could be another connection's value, and an unmatched delivery went to the internal fallback consumer instead of the one you installed. `IChannel.CurrentQueue` is still reset by recovery, so the empty-queue-name convenience does not survive a connection blip.

## A consumer's shutdown reason

No longer reports a shutdown already recovered from (#2006):

- `AsyncDefaultBasicConsumer.ShutdownReason` is cleared when a consumer is registered, including by automatic recovery. The value can now return to `null`, so copy it to a local before dereferencing it. It can also now rest at `null` with `IsRunning` false after a real shutdown, which a health check reading only `ShutdownReason` cannot see; #2016 carries that.

## Channel recovery handlers

No longer deadlock recovery (#2038):

- A channel `RecoveryAsync` handler that declares topology, registers or cancels a consumer, or closes its channel no longer wedges automatic recovery permanently. The handler used to be invoked while the connection held the lock guarding its recorded topology, and recording an entity re-takes that lock, so the handler waited on a holder that was waiting on it. The failure was silent and total: the connection still reported itself open, no recovery-failure event fired, and topology calls on unrelated new channels blocked until the process ended. Every release from `v7.0.0` to `v7.2.2` is affected. A handler that passed a real cancellation token to `QueueDeclareAsync` and three other methods escaped; the rest did not.
- Handlers now fire once every channel has recovered, rather than one at a time as each channel recovers. If you subscribe to `IRecoverable.RecoveryAsync` on a channel, which needs a cast since `IChannel` does not inherit it, your handler now sees a connection whose channels have all been recovered, along with topology and consumers where `TopologyRecoveryEnabled` is on. `RecoverySucceededAsync` has not fired yet. A later channel failing with an exception defers the earlier channels' handlers to the attempt that succeeds; a channel that is merely disposed does not.
- Two things this does not cover. The four `TopologyRecoveryFilter` predicates and the four `TopologyRecoveryExceptionHandler` conditions still run with that lock held; they are synchronous, so reaching the hang needs sync-over-async, but it is the same hang, tracked as #2043. And closing the connection from a handler still waits out `RequestedConnectionTimeout`.
- One thing that became reachable. Closing a different channel from a handler now works rather than deadlocking, and that channel's own handler then runs against a closed channel: any topology call it makes throws `AlreadyClosedException`, which surfaces on `CallbackExceptionAsync`.

## Connection shutdown and recovery reliability

- Application `ConnectionShutdownAsync` handlers now run after the connection's channels have closed (#2005). An internal pre-shutdown step runs and is awaited first, so a handler no longer observes half-open channels. This came out of deadlocks reported against a library that takes a lock in its shutdown handler. If you depended on the old ordering, application handlers before session teardown, this changes for you.
- A connection could stop recovering permanently (#2004). A race in the recovery loop meant a connection that reopened and then quickly dropped again was never recovered: it stayed down for good, with automatic recovery reporting itself enabled and nothing raised.
- After automatic recovery, an exception thrown by a channel's `BasicAcksAsync`, `BasicNacksAsync`, `BasicReturnAsync`, `FlowControlAsync`, `ChannelShutdownAsync` or `RecoveryAsync` handler, or a connection's `ConnectionBlockedAsync`, `ConnectionUnblockedAsync` or `ConnectionShutdownAsync` handler, reaches that channel's or connection's `CallbackExceptionAsync` handlers (#2092). Only handlers added before the first recovery used to see it.
- `ConnectionRecoveryErrorAsync` is now raised when recovery fails after it has reconnected, during topology or channel recovery, as its documentation states (#2014). It was raised only when reconnecting failed, so a subscriber saw nothing while topology recovery failed and retried. A handler that awaits `CloseAsync` on the connection waits for recovery, which is running the handler, so the close stalls until `RequestedConnectionTimeout`; this was already true of the reconnect case.
- Automatic recovery no longer stops for good when the broker's host accepts the TCP connection but then never answers (#1871). Each step of opening a connection now has a time limit: the TLS handshake shares `RequestedConnectionTimeout` with the TCP connect, and the wait for `connection.start`, `connection.secure` and `connection.tune` uses `HandshakeContinuationTimeout`, 10 seconds by default. The last two used `ContinuationTimeout` before, and the first two had no limit. A failed attempt raises `ConnectionRecoveryErrorAsync` and recovery tries again; `CreateConnectionAsync` throws `BrokerUnreachableException`. A broker that takes longer than these limits to answer, which 7.0 to 7.2 waited for, now fails the attempt: raise the limit if that is expected.
- `CreateConnectionAsync` now waits for `connection.open-ok` (#2000) before returning, so a `channel.open` can no longer be sent before the connection is ready.
- Five hang and deadlock fixes land in this release (#1960, #1921, #1976, #1930, #1827), along with two RPC fixes: spurious continuation timeouts (#1964) and a late reply tearing down the whole connection with a 541.

## An RPC timeout is cancellation, not `TimeoutException`

Documented rather than changed (#1996):

- A protocol operation that exceeds `ContinuationTimeout` completes as cancelled, so the awaiter sees an `OperationCanceledException`. This describes existing 7.x behavior, but it was undocumented, and the dead code that attempted a `TimeoutException` it could never deliver is now gone. Code carried over from 6.x that catches `TimeoutException` around an operation such as `QueueDeclareAsync` has never run on 7.x. To tell a timeout from your own cancellation, test your own token: if it is not cancelled, the operation timed out. `v7-MIGRATION.md` carries the rest, including why comparing `ex.CancellationToken` against your own does not work.

## Dependencies and deprecations

- **`System.Diagnostics.DiagnosticSource` is now a dependency for `net8.0`, not only `netstandard2.0`, and the floor rises from 8.0.1 to 9.0.4.** `net8.0` consumers acquire a package reference they did not have. The client needs it on every target framework because the tracing code calls `Activity.AddException`, which the in-box `Activity` on `net8.0` does not provide.
- **`Headers.XQueueMode` is now `[Obsolete]`**, because classic queue v1 was removed in RabbitMQ 4.3. A build using it gains a warning, and fails under warnings-as-errors.
- **Four new `ExchangeType` constants (#1922)**, `ConsistentHash`, `LocalRandom`, `ModulusHash` and `Random`, so `ExchangeType.All()` now returns eight values rather than four. That matters if you use it as an allowlist.
